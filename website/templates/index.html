Three commands

No changes to your project and no dependency: leanprof builds its runtime for your Lean version (4.34 and later) and puts your normal build back afterwards.

  1. Install the command.

    $ git clone https://github.com/unbalancedparentheses/leanprof && sh leanprof/scripts/install.sh

  2. In your Lake project, run an executable with its arguments.

    $ leanprof run myapp -- args

  3. Ask why each copy happened.

    $ leanprof explain

Then leanprof sample for CPU time with Lean names, leanprof stat for one screen of everything, and leanprof elab for compile time. The getting started guide walks through each.

Where you read it

On real code

Profiled from outside, without changing the projects. Every number below is from the linked write-up.

lean-compiler-backend

run --allocs, explain

A QBE-compatible compiler written in Lean. Its tokenizer made 4,066,775 of the 11,946,202 allocations needed to compile zlib. The fix, commit 4864dd2, is now on the project's main branch: 8,572,024 allocations for the whole run, −28%, with byte-identical output.

The first version of that fix was 30 times slower, and one leanprof run showed why: 91,020 copies of the token array, 6.84 GiB. leanprof explain also traced 121,054 copies in CFG.build to arrays pushed while still held by an outer array.

doc-gen4

sample, run

In the pass that renders the API docs to HTML, two thirds of its CPU time is one SQL query, getContainedNames, whose cost grows with the square of the number of declarations in a module. And 12.7% of the CPU time is threads waiting for SQLite's global memory mutex, which SQLITE_DEFAULT_MEMSTATUS=0 removes.

In the analysis pass, every declaration copies its module's member array: 29,026 copies, 69.9 MiB, quadratic in the size of a module.

LeanProfiler

compiler wrapper

Another Lean profiler, whose cost per span grows with the number of events recorded: 4.6 µs at 1,000 events, 20.1 µs at 4,000, 88.5 µs at 16,000 (leanprof over the same counts: 15.9–17.8, 8.9–17.0 and 10.0–11.6 ns).

leanprof found why without a single annotation in LeanProfiler: 12003 copies, 123.0 MiB, in reserveSpan for 4,000 spans. Its state lives in a mutex and is read with a second reference, so every span copies every event recorded so far.

Batteries

elab --project

The compile time of all 195 modules, profiled in 17.0 s, against 13.3 s for lake build from clean. In one session on the same machine, leanprof took 16.8 s and lean-source-profiler 102.9 s in compact mode and 152.3 s in detailed mode, on 263 files with tests and scripts (comparison).

Termination and bounds proofs are about a quarter of all elaboration: decreasing_tactic alone is 216.5 M heartbeats, 14.4%. An iterator definition is unfolded 24,369 times from ordinary RBTree proofs.

Also: verso, lean-regex, concrete, and the accuracy benchmark against workloads with known answers.
